## Loop benchmark

`bun scripts/bench-run-loop.ts` runs `runChat` against a scripted `MockProviderClient`, so provider time is zero. Each
shape gets 20 warmup and 200 timed runs. Two back-to-back runs on the dev machine (Apple Silicon, Bun 1.4.0):

| Shape | Events | p50 (run 1 / 2) | p95 (run 1 / 2) | RSS delta |
|---|---|---|---|---|
| (a) text-only, 1k-message history | 4 | 0.011 / 0.012 ms | 0.025 / 0.026 ms | 12.7 / 13.6 MB |
| (b) 10 tool calls (10 × 1) | 44 | 0.047 / 0.045 ms | 0.062 / 0.064 ms | 13.0 / 9.9 MB |
| (c) 100 tool calls (10 × 10) | 314 | 0.229 / 0.225 ms | 0.314 / 0.351 ms | 5.7 / 6.5 MB |

How to read these numbers:
- The loop's own overhead is microseconds. Real turns are dominated by provider latency, which this benchmark
  deliberately excludes.
- p95 varies about 10% between identical runs, so the regression gate for M1 is **p50 within ±15%** of these numbers on
  the same machine, compared across three runs.
- The RSS delta includes GC heap growth and is not a leak signal at this run count.

### M1 rerun (after the loop split and hooks, same machine)

These are the M1 regression checks. Each figure is the median p50 of three runs of `bun scripts/bench-run-loop.ts`,
with no hooks configured:

| Shape | M0 p50 | M1 p50 | Δ |
|---|---|---|---|
| (a) text-only, 1k history | 0.0115 ms | 0.013 ms | +13% (~1.5 µs) |
| (b) 10 tool calls | 0.046 ms | 0.051 ms | +11% |
| (c) 100 tool calls | 0.227 ms | 0.250 ms | +11% |

All three shapes are within the ±15% gate. The cost is two levels of `yield*` delegation per event: the model step and
the tool batch are separate generators. In absolute terms it is microseconds per turn, against provider latency
measured in hundreds of milliseconds.
