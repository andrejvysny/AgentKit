# H1.1 Approvals in Chat (AgentKit)

Hardening plan, package H1.1, blocker B1, decision D2 ("fix the executor; do not hide `memory_forget`"). OneMind side: `docs/evidence/hardening/H1.1.md` in OneMind.

"Done when": through OneMind's routes, approve gives the effect and a result; deny gives a denial result; neither gives "result missing".

## Finding

Reproduced, for the approve half. `ChatExecutor` (`rust/crates/chat/src/chat.rs`) called `session_run::resolve_approved_calls` only when the turn was a session turn. A plain chat (no session descriptor, task kind `chat.turn` submitted by `submit_chat`) got an empty approvals map and no resume calls. After an owner approved, the turn resumed, the approved call never ran, and history reconciliation answered the declared call with a synthetic `tool_result_missing`.

The deny half did not reproduce. `answer_human_request` writes the `approval_denied` record for any parked request, session or not, and history assembly hands it to the model. The new deny test passed before the change. FINDINGS F7 says "approve and deny cannot be told apart"; that was true only in the sense that neither ran the tool. The model did see `approval_denied` on a denial.

Checked before the change: `ParkSink` stores the request under `task.scope_id`, and the resolver queries by `chat_id`. `submit_chat` sets `scope_id = chat_id` (`chat.rs`, `ChatHostExt::submit_chat`), and OneMind's chat submission refuses a task whose `scope_id` differs from its chat (`onemind-backend/src/turn_submission.rs`). So the plain-chat request is found by the same query.

## What changed

- `rust/crates/chat/src/chat.rs`: `resolve_approved_calls` now runs for every turn. Steer backfill (`backfill_applied_steers`) stays session-only. The resolver itself is unchanged: it still takes only answered approvals that target this task and carry the store's approve marker, matches each against the declared call's argument digest (native or TypeScript canonicalizer), honours the approval and uncertainty generation, and writes `approval_mismatch` for an answer that names other arguments. Admission still spends each grant once through the durable receipt.
- `rust/crates/chat/tests/chat_approvals.rs` (new): a plain chat with a guard that asks for every `forget` call, answered through `SqliteStore::answer_human_request` as `AnswerActor::Owner` (the call OneMind makes). Each test asserts on the request the model receives after the answer, not only on task status.
- `rust/crates/chat/tests/session_runtime.rs`: the interrupt test's fixture warms the schema validators first (below).
- `scripts/known-failures.json`: the interrupt test's intermittent entry is removed. The Rust list is now empty.

## The intermittent interrupt test

`session_runtime::a_mid_run_interrupt_parks_and_the_resumed_turn_finishes_without_replay` was listed as intermittent in H0.2 ("the slow tool body never starts").

Cause, found with temporary instrumentation (a logging `Runtime` and timestamps around the executor's preparation steps; all removed):

- In every failing run, `host.run_once()` returned `Err(Store(LeaseLost))` about 156 ms after the claim, with zero provider requests and zero events. Passing runs entered the tool body at about 165 ms.
- Between two of the executor's store calls there was a gap of about 140 ms with no heartbeat. It is inside `prefix::frozen_tools`, in `agentkit_sessions::read_session_prefix`, in `agentkit_contracts::validate_schema`. The first validation in a process initializes a `OnceLock` that compiles every schema in the embedded contract bundle. That is about 140 ms of synchronous work in a debug build, and it blocks the attempt's future, which shares one `select!` with its lease heartbeat.
- The fixture sets `lease_ttl_ms: 150` (so the heartbeat runs every 50 ms). A 140 ms stall plus the rest of the preparation outlives the lease. The next fenced write is refused with `LeaseLost`, the attempt ends, and the tool body never starts.

This is a test timing problem, not a product race. The lease fencing behaved correctly: it refused an attempt whose lease had expired. The production TTL is 30 s, and the stall happens once per process. The H0.2 run's "suspected race" is withdrawn. Rates: 13 of 30 isolated runs failed at a load average of about 3 before the fix.

Fix: the fixture calls `agentkit_contracts::validate_schema` once before the attempt, so the one-time compile happens outside the lease. No assertion, timeout or TTL changed. After the fix: 0 of 40 isolated runs failed (load average about 2.1), and 64 of 64 passed with eight copies running in parallel (load average about 10).

My change to `chat.rs` does not affect this test: for session turns the resolver ran before and runs now, in the same order after the steer backfill.

Observation for the owner, not changed: the first `validate_schema` in a process blocks an async worker for about 140 ms in debug builds (less in release). It is far below the production lease, so it is a latency note only.

The first `buntest` run failed on one test outside the known list: `packages/core/tests/agent-loop-hooks.test.ts > runAgentLoop hooks > hooks: [] is byte-identical to runChat`. The two traces differed only in a tool event's `durationMs` (0 against 1). This is a TypeScript test of `packages/core`, which this package does not touch; it compares two runs whose tool calls can straddle a millisecond boundary. Run alone five times it failed once. The rerun passed. It is not added to the known-failures list. Cause: `normalizeTrace` (`packages/testing/src/golden/golden.ts`) strips `timestamp` and `eventId` but keeps `durationMs`, which is wall-clock. Proposed fix, for the owner to schedule: zero `durationMs` in this test's comparison.
