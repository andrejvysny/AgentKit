# H1.1c Denied call result in the stream (AgentKit)

Hardening follow-up to H1.1/H1.1b, added by the main session from the live OpenAI evaluation of 18 Nov. OneMind side: `docs/evidence/hardening/H1.1c.md` in OneMind.

## Finding

Reproduced. When the owner denies a parked call, the store's answer writes the denial as the call's tool record (`approval_denied`). The resumed turn hands that record to the model, so the model reads the denial. But no run event is written. A host that renders tool results from the durable event log (OneMind's SSE projection) therefore showed the call with `tool_call` and `tool_running` and no result.

Evidence: `acceptance-runs/2026-11-17T230221Z-eval/trials/default/gpt-6.2-sol/mem-forget-denied-sk/trial-01`. The provider request `provider/00003-request.json` carries `function_call_output … approval_denied`. `chat1-turn01/sse.ndjson` has `tool_call` and `tool_running` for the `memory_forget` call id, then `reset` and `done`, and no `tool_result`.

## What changed

- `rust/crates/chat/src/chat/session_run.rs`: `resolve_approved_calls` (which runs for every turn since H1.1) first calls `announce_denied_calls`. For each answered approval of this turn whose answer was a denial, and whose tool record carries `approval_denied`, it emits one `run.tool.failed` with `{toolCallId, toolName, errorMessage, errorCode: "approval_denied"}`. That is the event shape a tool refusal already uses. A call that already has a `run.tool.succeeded` or `run.tool.failed` gets none, so a retried attempt never emits twice. No new event type, no change to the answer path, the approval binding or the record the model reads.
- `rust/crates/chat/tests/chat_approvals.rs`: two tests.

## Tests

| Test | Before | After |
