# H1.5 Responses parser (AgentKit)

Hardening plan, package H1.5, blocker B5 (FINDINGS F6c). Spec: `06-native-tool-use-spec`, TU-09 ("every emitted call receives a result on every provider path").

"Done when": the fixture with an unoffered name yields the text, the other calls and one failure result.

## Finding

Reproduced. `rust/crates/providers/src/responses_state.rs`, `tool_call` (lines 510-513 at `c01190cc`), returned `unknown_tool` for a `function_call` whose name was not in the request's tool list. `ResponsesState::finish` propagates that error, so the whole reply failed: the run ended with `run.failed`, the reply's text and its other valid calls were dropped, and the model got no result for any call. The Chat Completions parser does no such check; it passes the name to the call pipeline, which answers it with a per-call failure.

The check dates from the provider extraction (`01d14f80`) and was carried over from the strict TypeScript parser. No commit or ADR gives a reason for aborting.

## What changed

- `rust/crates/providers/src/responses_state.rs`: `tool_call` no longer checks the name against the offered tools, and no longer takes the tool list. An unoffered name reaches the call pipeline (`agentkit_core::call_pipeline::resolve_failure`), which already answers it with the three closest offered names and a pointer to `tool_search`. The failure class is `unknown_tool`. A deferred tool called by name gets the existing `tool_deferred` teaching message. The nearest names are computed in core, as for Chat Completions, not in the provider.
- Unchanged on purpose: a `function_call` whose `namespace` is not `agentkit` still fails the reply with `unknown_tool`. A built-in call (`apply_patch_call`, `shell_call`) to a built-in the request did not offer still fails the reply (`builtin_call`; `providers/tests/openai_builtin.rs::a_built_in_call_the_request_did_not_offer_is_refused_by_the_parser`). Both are protocol faults rather than a model naming the wrong tool, and B5 does not cover them.
- `rust/crates/eval/fixtures/http/responses_unoffered_tool_mixed.sse` (new): one reply with text, an offered `read_file` call and a call to the unoffered `read_notes`, stream-consistent with its `response.completed` output.
- `rust/crates/eval/tests/tool_pipeline.rs`:
  - The existing test `responses_refuses_an_unoffered_tool_loudly_and_runs_nothing` asserted the abort. It is now `responses_answers_an_unoffered_tool_with_a_failure_and_runs_nothing`. It uses the same `responses_unknown_tool.sse`, plus `responses_answer.sse` for the follow-up request that now happens. Changed assertions: `run.completed` instead of `run.failed`; the call's record has `outcomeClass: unknown_tool`; two requests instead of one; the follow-up returns one result, for `call_unknown`. Kept: nothing reached the tool.
  - New: `responses_keeps_text_and_valid_calls_beside_an_unoffered_tool` (the "Done when").
- `rust/crates/eval/src/run.rs`: a doc comment that stated the old abort is corrected. Code unchanged.

The new test asserts that:

- the run completes;
- `call_valid` has outcome `ok` and `call_unknown` has `unknown_tool`;
- only `{"file_path":"a.txt"}` reached the tool;
- the follow-up request still carries the reply's text as a `message` item;
- it answers `call_valid` then `call_unknown`, once each, in call order;
- the failure output names `read_notes`, the nearest offered tool `read_file`, and `tool_search`.
