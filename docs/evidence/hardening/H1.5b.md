# H1.5b Chat Completions: function tools refused with a reasoning effort (AgentKit)

Requested by the main hardening session on 18 Nov 2026, after the live OpenAI runs. It is not in the hardening plan. It sits beside H1.5 in `crates/providers`.

## Finding

Reproduced from live evidence (`acceptance-runs/2026-11-17T222021Z/agentkit/probe/{gpt-6-luna,gpt-6.1-terra,gpt-6.2-sol}/probe-report.json`). Every Chat Completions request with function tools failed with:

```
HTTP 400 {"error":{"message":"Function tools with reasoning_effort are not supported for gpt-6-luna in /v1/chat/completions. To use function tools, use /v1/responses or set reasoning_effort to 'none'.","type":"invalid_request_error","param":"reasoning_effort","code":null}}
```

AgentKit's Chat Completions lane could therefore not call tools on these models. The Responses lane works.

**The requested design would not have fixed it.** The main session's brief said to retry without the field. The probe's captured tool requests (`.../gpt-6-luna/provider/00001-request.json` to `00004`, `00010` to `00015`) carry only `messages`, `model`, `tool_choice` and `tools`, with no `reasoning_effort`, and still got this 400. The model's default effort counts. Dropping the field would only re-send the same refused request. The provider therefore retries with `reasoning_effort: "none"`, as the error text asks.

## What changed (`rust/crates/providers`)

- `src/chat_completions_effort.rs` (new): the refusal test is a 400 whose JSON `error.param` is `reasoning_effort`, on a request with at least one tool. It also holds the forcing helper (sets `reasoning_effort` to `"none"`, false when it already was) and `Refusals`, the set of models refused this way. `Refusals` is owned by the provider instance and shared by its clones. A first draft used a process-global static like the Responses lane's `summary_rejected`, but `check-arch` refused it (rule R5, no new statics) and the allow-list may not grow.
- `src/chat_completions.rs`, `send`:
  - A model this provider instance has seen refused sends `"none"` from the first request.
  - Otherwise such a refusal is retried once with `"none"` and the model is remembered.
  - The existing `max_tokens` to `max_completion_tokens` retry is unchanged; it is tracked by a flag instead of the attempt number, so the two retries can combine (at most three requests).
  - Every request still consumes the `providerRequests` budget.
  - When the effort was forced, the stream yields a `reasoning_effort_dropped` warning (an existing `AiRunWarningCode`) naming the model.
- Not retried:
  - any other 400;
  - a refusal of a request without tools (the effort is kept);
  - a second refusal after `"none"` was sent (it fails as before, after two requests).

Effect the owner can see: on these models, Chat Completions tool calls now run with reasoning off, and the run carries a warning. Reasoning with tools on these models needs the Responses lane. That routing choice is the host's or profile's, not this package's.

## Not verified

- Live: that these models accept `reasoning_effort: "none"` with tools on `/v1/chat/completions`. The error text says so, but no paid call was made here. Re-run the probe (P-checks with tools) on gpt-6-luna, gpt-6.1-terra and gpt-6.2-sol.
- Servers that blame `reasoning_effort` but reject `"none"` too. They now get one extra request and then fail as before.
- The memory lives as long as the provider instance. A host that builds a new provider per run pays one refused request per run, which the warning makes visible. A provider that later accepts effort with tools is tried again with a new instance.
