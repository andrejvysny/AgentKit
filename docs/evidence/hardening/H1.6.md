# H1.6 Validation message (AgentKit)

Hardening plan, package H1.6, blocker B6 (FINDINGS F3). Spec: `06-native-tool-use-spec`, TU-10 (a failure says what happened, why, and the next step) and TU-07/TU-08 (old parameter names accepted as recorded aliases).

"Done when": the error names the extra property and lists the allowed ones; an old name is accepted and recorded.

## Finding

Reproduced, and wider than the review said.

- `rust/crates/contracts/src/properties_validation.rs:229` (at `df39717e`) answered every failure of its `additionalProperties`/`patternProperties` override with `property rejected by ECMAScript schema constraints`, located at the object, so the tool registry rendered it as `Invalid arguments for <tool>: : property rejected ...`.
- jsonschema hands the checks of declared properties to `additionalProperties` when that keyword is `false` or a schema. Since the lint closed every tool schema, the override also swallowed the nested error of every declared property with a bad value, not only extra properties.
- One level down, the JavaScript-number keywords (`numeric_validation.rs`: `type`, `enum`, `const`, `minimum`/`maximum` and their exclusive forms, `minLength`/`maxLength`, `minItems`/`maxItems`, `minProperties`/`maxProperties`, `uniqueItems`) all answered `value rejected by JavaScript numeric schema semantics`. The Ajv profile's `format` and `multipleOf` (`ajv.rs`) answered `value rejected by AgentKit's Ajv compatibility profile`. So even with the property named, the reason was not.

**F3's attribution is off.** F3 says Qwen sent the extra fields `rationale` and `owner_requested`. Both are declared in `memory_propose`'s schema. The rejected call (`acceptance-runs/diag-qualification-qwen/provider/00035-request.json`, the tool message answering the `memory_propose` call made through `tool_call`) carried `"scope": "global"`, and `scope` allows only `user`, `project` and `agent`. Under H1.6 that call now reads `/scope: "global" is not one of "user", "project", "agent"`. FINDINGS.md should be corrected; it is not edited here because it lives outside this repository.

**The old-name half did not reproduce at HEAD.** B6 says the closed schema rejects documented old names before the tool sees them. Since T1.3/T1.6, `ToolRegistry::register` collects each tool's `Tool::arg_aliases()`, and the call pipeline (`core/src/call_pipeline.rs`, `prepare_resolved`) maps them before `registry.validate_input` runs. This holds for direct calls and for calls through `tool_call`. The new end-to-end test `an_old_parameter_name_passes_a_closed_schema_and_is_recorded` passed before this change. It stays as a pin. No change was needed in core. `runtime/tests/tool_schema_lint.rs` covers the shipped tools' renames.

## What changed

All in `rust/crates/contracts`. Validity is unchanged: each keyword still decides with the same `is_valid`, and only builds its error after deciding.

- `src/properties_validation.rs`:
  - `valid_property` becomes `rejection`, which returns why a property fails: undeclared on a closed object, a value its schema rejects, or a schema that was not compiled. The decision logic is the same, branch for branch.
  - `validate` describes the first rejected property in the caller's order:
    - **Bad value:** the nested validator's own first error, with its instance path prefixed by the property's path, for example `/options/depth`.
    - **Undeclared property:** an error at that property's path naming every undeclared property sent and the allowed properties and patterns, with "Remove it (them) or use an allowed property".
  - The old text remains only as a fallback if the schema context is gone, which a compiled validator never reaches.
  - Pattern entries keep their source text for the message.
- `src/numeric_validation.rs`: each rule says what the value broke:
  - type: `"3" is not of type "integer"`;
  - enum: `"c" is not one of "a", "b"`, listing up to 20 values;
  - const: `"y" is not the required value "x"`;
  - bounds: `0 is less than the minimum 1`;
  - lengths: `"a" is shorter than 2 characters`, and `has more than 1 items` for arrays and objects;
  - `the items are not unique`.

  Values are shown as JSON and cut at 60 characters.
- `src/ajv.rs`: `"monday" is not a valid "date"` and `7 is not a multiple of 5`.
- Draft-07 wire DTO validation (`validate_schema`) uses the same keywords, so its errors carry the same detail. No test or client compared the old texts (searched AgentKit and OneMind sources, fixtures and docs).

What the model reads now, using F3's call and a call with two extra fields:

```
Invalid arguments for memory_propose: /scope: "global" is not one of "user", "project", "agent". ...
Invalid arguments for memory_propose: /reason: properties "reason", "confidence" are not allowed here; the allowed properties are "kind", "owner_requested", "rationale", "scope", "text". Remove them or use an allowed property. ...
```

The core wrapper text (`Invalid arguments for <tool>: <path>: <error>. Fix the arguments and call again.`) and the failure codes (`schema_invalid`, `invalid_arguments`) are unchanged.
